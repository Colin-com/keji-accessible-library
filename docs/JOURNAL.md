## 2. 价值红线（内容侧，先于一切）

写无障碍题材最容易翻车的地方，也是本项目的自检项：
1. **社会模式**优先：障碍来自环境与设计，不来自人的缺陷。
2. **Nothing about us without us**：残障角色有主体性，会拒绝"好意"，不是等待被拯救的道具。
3. **拒绝怜悯叙事与说教**：价值观只通过后果、关系、生活变化呈现。
4. **事实可溯源**：每条知识/法规/技术都有出处。科普游戏讲错事实比不讲更糟。

## 13. 三处观感缺陷的修复（"能玩"之后才发现的问题）

用户逐字反馈：**"游戏的档案库里面有些莫名其妙的问号，像素人物的特征不明显，在剧情推进的过程中人和场景没有出现相应的变化"**。
这三条都不是功能 bug——机器验收（能点、能推进、能到结局）全绿也照样存在，**只有把画面当画面看才会发现**。

| # | 现象 | 根因（查证后） | 修法 |
|---|---|---|---|
| ① | 档案库"莫名其妙的问号" | 不是编码问题：`renderArch()` 把**未解锁条目**渲染成 `<b>？？？</b><p>尚未解锁</p>`，10 条里只解锁 3–5 条 → 一眼望去全是问号 | 改成 `<b>未解锁</b>` + **分类标签**（取自 `tags`）+ "在剧情中接触到相关内容后自动收录"；补 CSS 让 `.arow.locked p` 也显示 |
| ② | 像素人物特征不明显 | 四个角色（我/小舟/馆长/学姐）**共用同一张 7×9 字符画**，只换外套颜色；且我和小舟都是蓝色 | 改为四张独立 9×16 字符画（各自发型/眼镜/领带/背包/裙子/轮椅），小舟换青绿（`q`）与我的蓝（`j`）区分；小舟多画**大轮轮椅**（15×16） |
| ③ | 剧情推进时人和场景不变 | `stage()` 只在开局调用一次，此后没人调用 → 全程同一张静态场景 | 新增 `SCENES` 表（**30 个节点逐一定义**：在场角色 + 位置 + 道具 + 光线 + 地点标签 + 提示），`goto()` 每步调 `setScene(id, speaker)`；新增 10 种道具字符画（门/书架/窗/台阶/坡道/盲道/服务台/低位服务台/施工锥/告示牌/绿植）与导盲犬角色 |

**验收（不靠截图判据，读 DOM + 已渲染像素）**
- 30 个场景逐个 `setScene(id)` → 角色名单 / 道具数量 / 透明度 / 光线 class 与 `SCENES` 定义**逐字一致**（0 处不符）
- 真点着玩通一遍：**0 JS 报错、15 幕场景各不相同、3 次选择、到结局**
- 场景序列（可证 ③）：北门台阶〔我〕→ 小舟登场〔我/小舟〕→ 量尺寸 → 通道最窄处 → 服务台 → 入口〔我/小舟/导盲犬 + 盲道〕→ 三种做法〔+馆长〕→ 缓坡 → 占绿地 → 送书〔+学姐〕→ 造价表〔施工锥〕→ 立项〔dusk〕→ 结局〔坡道/低位台/盲道〕

- 新增 `tools/check_scenes.py`：字符画行宽一致 / SCENES 与剧情节点**恰好互相覆盖** / 素材引用有效 / 无占位问号 —— 首次运行即抓出"服务台字符画有一行少 1 像素"的错位

**本轮新增的坑（第三次踩"验收自欺"）**
| 坑 | 后果 | 教训 |
|---|---|---|
| `?screen=scene&node=X` 用 `goto(X); finishTyping();` 定格 | `finishTyping()` 会 `setTimeout(pendDone,120)` → **120ms 后自动推进到下一幕**，把定格画面覆盖掉；抽查三个节点返回的是**同一幕**，等于给出了三张假证据 | 定格截图必须**掐断 `pendDone`**（清 typing 定时器 + `pendDone=null`）；证据要"每张不同 md5 **且** DOM 状态与预期一致"双查，不能只看文件存在 |
| 用 `#choices` 点选项、`#box` 推进 | 真容器是 `#opts`、真推进是打字机跑完自动下一步（点击 `#text` 只是跳过）→ 自动化"点了 88 次都没动" | 自动化点击前先读绑定真身，别凭印象写选择器 |

## 14. 档案库"没有同步"的真相（第 4 次验收自欺 + 一次真缺陷）

用户第二轮仍报**"然后档案库仍然没同步"**。逐层查下去，答案是**两条互相叠加的原因**，而且其中一条出在我自己的验收方式上。

**A. 现象本身不成立：玩家看到的是浏览器缓存的旧版。**
GitHub Pages 对 `web/index.html` 返回 `Cache-Control: max-age=600`；用户在我重建之前打开过页面 → 手上仍是旧代码，行为自然和旧版一致。
最直接的证据：**我自己的验收浏览器也中招**——第一次用 `goto_url()` 读 `buildStamp` 读到 `null`，必须加 `?v=<时间戳>` 破缓存才读到新值。等于我亲手复现了用户的现象。
修法：① 主菜单底部加**构建版本戳**（`构建 v4 · 117 节点 · 9 决策 · 10-11 17:15`），扫一眼即可自证新旧；② 对外一律发带 `?v=` 的链接；③ 验收流程固定用 `?v=` 破缓存（已写进本节纪律）。

**B. 真缺陷：解锁状态"看不见"，不是"没同步"。**
新构建里逻辑一直是通的（解锁瞬间 `0/10 → 1/10`、结局页 `已解锁档案 1/10`、回主菜单 `（跨局保留）`、刷新后 localStorage 仍存 `entry_turning_space`）。但档案条目**默认只显示标题、详情折叠**，而我给已解锁条目加的"已解锁"绿标被放进了折叠区 `<p>` 里 → 玩家视线里没有任何变化，判定为"没同步"完全合理。
修法：标记移到**标题行**（`<b><span …>已解锁</span>标题</b>`）。验收用 `innerText`（可见文本）而**不是** `innerHTML`：`innerHTML` 有标记但 `innerText` 没有 → 就是"折叠区里的标记"这一类的判定法。

| 坑 | 表现 | 教训 |
|---|---|---|
| 拿缓存页面做验收 | 自己的 `buildStamp` 读到 `null`，一度误判"注入失败" | 任何 Web 验收都带 `?v=<时间戳>`；线上核验要同时比对"服务器文件"与"渲染结果" |
| 用 `innerHTML` 判断可见性 | 绿标"在 DOM 里"但玩家看不见 | 可见性用 `innerText` / `getComputedStyle` 判，DOM 有 ≠ 人眼有 |
| 修复只做在逻辑层 | 逻辑全绿、观感为零变化 → 用户复报同一问题 | 涉及"看得见的变化"的修复，验收判据必须落在**人眼可见的那一层** |
| 计数写死在文案里 | 档案从 10 条扩到 14 条后，README/微信材料仍写"10 条" | 数字必须由数据算出来（分母已用 `ARCHIVE.length`）；文案里的数字要跟着改 |

## 16. 同步问题收口：把"不可见的状态"做成页面自己会说（v6）

用户第三次反馈**"档案库仍然没同步"**。我先把程序能走的路径全走一遍（真点击通关 / 回主菜单 / 再开一局 / 刷新页面 / 直接读 localStorage）：**6/14 → 6/14 → 6/14 → 6/14**，代码侧无懈可击。既然我复现不出，就不能再靠"你刷新一下"把问题推回给用户——改成让页面自己暴露变量：

| 措施 | 作用 |
|---|---|
| 每张截图/每次 HUD 刷新都先读盘合并（`mergeArchive()`，`hud()` 首行） | 任何代码路径都不可能"丢掉"已解锁条目 |
| 档案库面板底部新增**诊断行**：`本机记录 N 条 · 本次会话 M 条 · 跨局保留正常 · 构建 v6…` | 数据不一致时**肉眼可见**，不用猜 |
| 启动时探测 localStorage 可用性（写探针键） | 无痕/隐私模式下会显示 **⚠ 本机存储不可用——解锁只在本次打开期间有效**（这种环境的现象与"没同步"完全一样，此前无法区分） |
| 主菜单底栏加**「刷新到最新版」按钮**（`location.replace(pathname+"?v="+Date.now())`） | 一键破缓存，不需要用户懂 Ctrl+Shift+R |
| 版本戳提升到 `构建 v6 · 117 节点 · 9 决策 · 时间`；根跳转页 `index.html` 也带 `?v=6` | 线上/本地/旧缓存一眼可辨 |

**教训（本轮核心）**：连续三次"我测通了、用户说没好"时，**问题在验收口径而不在代码**——我第一次的判断（浏览器缓存）虽然是真的，但把举证责任推给了用户（"你按 Ctrl+Shift+R"）。正确做法是**把状态做成页面自己会说的东西**：计量、诊断行、存储可用性告警、一键刷新。这样下一次无论是不是环境问题，第一屏就能定位。
